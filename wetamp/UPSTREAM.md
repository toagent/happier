# Happier 上游升级约定

用户要求 WeTAMP 定制兼容 fork 上游代码升级。本文件定义实现时必须满足的维护与验收要求；当前仅完成源码入口核对和方案编写，未执行一次真实上游合并或兼容测试。

对应需求为 [Y700 定制路线 R8](plans/y700-private-android-customization.md)。通用兼容规则沿用 [docs/compatibility.md](../docs/compatibility.md)，不在私有定制中另造协议或迁移标准。

## 1. 基线与维护分支

| 项目 | 2026-09-20 已核对状态 |
| --- | --- |
| 私有 origin | `https://github.com/toagent/happier` |
| 当前 checkout | `dev`，跟踪 `origin/dev` |
| 当前完整 HEAD | `56fd1ce5b0857f3c3da97332bdc53e3b95a570ef` |
| UI / CLI / server 标称版本 | `0.2.12` / `0.2.13` / `0.2.12` |
| 计划跟进的上游 | `https://github.com/happier-dev/happier`；前序选型来源，首次升级时再次核对来源与目标提交 |
| upstream remote | 此前仅发现 origin；本次没有添加 remote 或 fetch |
| 上游兼容结论 | 未验证；当前 fork HEAD 不等于已确认的上游发布基线 |

维护时保留上游 Git 历史；origin 指向私有 fork，upstream 用于获取核对后的上游。私有长期分支接收已验收的上游合并，升级候选先在隔离工作区/集成分支验证。分支名称由实施时决定，不为了本文现在切换分支。多人共享或已发布的私有分支优先 merge，不重写其提交历史。

每次发布记录：上游仓库、不可变 tag/commit、私有最终 commit、锁文件与工具链版本、UI/CLI/server/provider 版本、Android versionCode/runtimeVersion、制品校验值与验证结果。滚动 stable/preview tag 只用于发现目标；验收必须落到精确 commit/制品。更新上游代码不等于同时强制所有组件升级。

## 2. 定制归属与接入方式

| 定制类型 | 归属与方式 | 升级时检查 |
| --- | --- | --- |
| 包名、品牌、图标、默认服务地址、OTA | `wetamp/config/` 与 `wetamp/assets/`，使用 `apps/ui/app.config.js` 已有覆盖入口 | 配置解析、资源引用、包身份和构建上传范围 |
| 构建及维护入口 | `wetamp/scripts/`，调用现有 workspace/build/test 脚本 | 上游脚本参数、Node/Yarn/Expo/Gradle 兼容性、依赖打包范围 |
| 平板布局、审查入口、待处理展示 | `apps/ui` 原 owner；复用现有 pane、SCM、Inbox、settings 和主题 | 真实触屏操作、相关组件测试、设置读写 |
| twin-agent 接入 | `apps/cli/src/integrations/` 的定制集成及已有 daemon 生命周期入口 | 新建、resume、fork、handoff、恢复与共享队列限制 |
| 需要扩展的通信能力 | `packages/protocol` 与现有生产者/消费者，遵循当前能力协商 | 新旧 UI/CLI/server 的受影响方向 |
| 升级记录 | `wetamp/upstream/`，在首次实现/升级时建立 | 精确基线、定制接入点、迁移说明、测试与剩余风险 |

配置加载使用 `EXPO_APP_LOCAL_CONFIG_PATH` 指向 `wetamp/config/app.cjs`，由构建入口按当前 checkout 计算绝对路径。配置文件及入口均待实现；不能把本机绝对路径写入仓库或 CI。现有 `app.config.js` 中的 `require(candidatePath)` 和本地 override 合并是已核对接缝，具体值与构建结果仍需验证。

私有目录是配置、资源和维护资料的归属，不是复制业务实现的理由。运行时代码继续遵守所在包的依赖、编译与打包边界；若未来有真正跨包共用的代码，先按仓库既有 workspace 机制评估，不直接跨目录 import 未纳入发布包的 `wetamp/` 源码。

每个必要的上游接入点在实现时记录四项：修改原因、canonical owner/符号、消费方、决定性的验证命令。没有行为变化的纯配置无需制造一套兼容适配器。通用修复与 WeTAMP 默认值分开组织，保持以后向上游贡献的可能；不得自动对外发布私有代码。

禁止用文件拷贝、postinstall 正则替换或每次重放同一补丁包覆盖上游；已合入 Git 的实现是代码事实源。不得对冲突批量使用 ours/theirs，也不得让旧定制整文件覆盖新上游。上游移动或重写 owner 时按功能意图迁移定制，删除已被上游实现替代的代码。

## 3. 升级必须覆盖的兼容边界

**源码与构建：**沿用 monorepo 的包管理器和锁文件。升级接入点可人工调整，要求结果可验证，不承诺永远零冲突。特别检查上游是否改变配置覆盖、Expo/React Native 原生插件、Metro/TypeScript 解析、CLI 打包和 Android target SDK。

**分批升级：**根据实际部署顺序验证新版 App/CLI 对旧 server，以及旧 App/daemon 对新版 server 的受影响核心操作。新增开发机交互能力必须先协商；不支持时仅该操作提示需要升级，保留可安全运行的现有功能。禁止因版本不匹配回退到不经过 twin-agent 的直接启动。

**持久数据：**新版读取实际已部署版的账号配对、密钥、设置、消息/草稿和任务状态。只有回退或共存真实可达时才要求旧版读取新版写入的数据，不维持所有历史 dev 版本的永久兼容。新增 WeTAMP 设置进入当前 canonical schema 的受管扩展，不建第二份同步设置；验证既有 reader 对新增字段的实际行为，不假设其会忽略或保留。

**发布身份：**保持正式包名、签名和设备配对连续；不能重用上游 OTA 项目把定制覆盖掉。上游 UI 版本号不直接充当私有 APK versionCode；运行时/native 依赖改变时按 Expo runtime 兼容规则区分 OTA。APK 回退使用同签名、更高 versionCode 的回退构建，且验证它能读取当前数据。

**server/数据库：**沿用上游 migration owner；已发布迁移不可改字节或改名。升级前备份并在测试副本验证真实数据迁移，明确回退需要哪个备份与停写边界；不能因 Git 能回退就承诺数据库可直接降级。

三端 provider 的指令、MCP、hooks 和权限语义属于实际工作能力；包装层或上游升级若改变加载方式，必须分别验证，不能用一次 hello-world 代替。

## 4. 每次上游升级流程

1. **确认目标。**记录当前实际部署版本和待合入上游的精确提交/发布证据，阅读相关 release notes，检查当前工作树。保护用户未提交修改，选择独立升级工作区。
2. **识别影响。**比较上次已验收上游基线到候选的 diff；对照定制接入点，识别 owner 变化、上游已实现的功能、协议/数据库/原生依赖变化。删除已无必要的私有重复实现。
3. **合并并适配。**保留上游历史，逐处解决语义冲突；检查合并后的最终代码及锁文件，不把 Git 自动合并成功当作行为不变。
4. **运行针对性验证。**先跑受影响配置/模块/协议测试和类型检查，再构建自有 APK；原生配置、打包或 provider 变更时覆盖相应真实路径。纯文档变更无需重跑完整产品矩阵。
5. **验证数据和现场流程。**按实际分批升级顺序测混合版本；Y700 覆盖安装保留配对与草稿，热点断线恢复、权限确认、原生 diff、本机 code-server、开发机队列和三端恢复均按影响面验收。
6. **记录并交付。**更新已验证基线、接入点、迁移/回退方法与执行证据。所有阻塞项解决后再进入发布步骤；提交、推送、部署遵循用户已有授权边界，不由升级脚本自动执行。

首次定制完整交付时，使用两个实际存在且可追溯的上游基线/候选跑通上述升级流程，作为 R8 的证据，不以等待尚未发布的未来版本为前提。未来每次跟进新版本重新验收。候选未选定或合并/运行验证未完成时，明确标记未验证，不以本文存在代替。

## 5. 最小升级记录

在实际升级时创建 `wetamp/upstream/<日期>-<候选短SHA>.md`，只记录以下必要内容：

- 当前部署的组件/制品版本，上次上游基线、候选精确来源与 SHA、私有最终 SHA。
- 受影响定制接入点、采用的上游变更、删除的私有重复实现。
- 实际可达的新旧组件组合、数据迁移与 APK/服务回退条件。
- 已运行命令、真机/网络场景、结果和证据位置；未验证项单列。
- 是否具备发布条件及仍需人工处理的事项。
